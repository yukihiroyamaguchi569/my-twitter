## はじめに

前回（[note-1.md](note-1.md)）では、第1〜2章のGoogleログイン実装と、思わぬハルシネーション騒動までを書きました。今回はその続き、第3章の投稿機能から、第10章のセキュリティ総まとめまでの記録です。

まずは前回の宿題だった第3章。`insert`でツイートを保存し、`select`（新しい順）で一覧を取得するところまで実装しました。本文の表示は最初から`textContent`を使ってXSS対策をしていて、我ながらちゃんとしていたなと思います。

## 2. 第4章 データ分離とRLS ——教材の"背骨"

### なぜ後から列を足すのは大変なのか

RLSの実装SQLを組み立てるとき、既存の投稿データに`user_id`を後付けする必要が出てきました。データは消してよかったので楽な方式で進めたのですが、その過程で「DBに後から列を足すのが大変なのは、NULL制約に引っかかるのも原因の一つなのかな？」と、ふと疑問がわきました。

まさにその通りで、NOT NULL制約は「これから入る行」だけでなく「すでに入っている行」にも適用される、という話でした。それを聞いて、じゃあ実務で大規模なテーブルに列を足すときはどうするんだろう、と気になって、別のDBを作って移行したりするのかをAIに聞いてみました。答えは「そこまではしない」で、nullableで追加→バックグラウンドで少しずつ埋める→NOT NULL制約、という段階的な手法が定石だと知りました。列1つ足すだけの話から、実務のオンラインスキーマ変更の話まで広がって、面白い寄り道でした。

### insertでuser_idを書かなくていい理由

RLSのSQLを解説してもらう中で、`default auth.uid()`の意味が分かった後、「insertの時にuser_idを渡さなくていいの？」と素朴な疑問が浮かびました。

答えは「渡さなくていい」。デフォルト値が自動で埋めてくれるのに加えて、`insert`用のポリシー（`with check (auth.uid() = user_id)`）が、たとえ他人のIDを指定しても弾いてくれる、という二段構えでした。「なるほど！なりすまし防止の意味もあるね！」と思わず声に出したくなるくらい、この瞬間にRLSの核心が腹落ちしました。「自動で正しく入る」だけじゃなくて、「不正に書き換えられない」まで保証している。これがこの章がいちばん大事にしている部分なんだと分かりました。

### 「あ、付録Cに解説があったよ」

RLSがPostgreSQL特有の機能で、MySQLには無いという話をしていたとき、自分でもう一度教材を読み返してみたら、実は付録Cにその話がまるごと書かれていることに気づきました。自分で見つけられたのは、ちゃんと理解が進んでいた証拠かなと思って、ちょっと嬉しかったです。

## 3. 【寄り道】第2章に舞い戻る ——コードはどこに書くの？事件

第4章が終わった後、ふと第2章のときに詰まった記憶がよみがえりました。ログイン確認の`getUser()`コードを、最初にブラウザのDevTools Consoleへ直接貼り付けたら、こうなったんです。

- `supabase is not defined`
- `import`文を貼ると `Cannot use import statement outside a module`

最終的には`main.js`に直接書いて解決したのですが、「元々はどうやるのが正解だったんだろう？」と気になって、ちょっとした調査を始めました。

### git考古学：main.jsはいつ生まれたのか

「main.jsってこの時に初めて作ったんだよね？」と聞いてみたところ、最初のコミットを掘り返してもらい、`counter.js`（Viteのデモ用ファイル）が同居していたことから、実は`npm create vite@latest`によるフロント雛形作成が先にあって、そこに認証コードを書き足していたことが分かりました。「そうだね、しかし前からあったわけじゃなくてこの時点でnpm createしたよね？」と、自分の記憶と時系列を確認し合いました。

### buildless vs Vite、そしてIssueを立てるかどうかの葛藤

教材全体を探しても`npm create vite`のような雛形作成手順がどこにも書かれていないと分かり、一瞬「これは教材の不備なのでは」とIssueを立てる方向で動きかけました。前回のanon key修正がうまくいった成功体験もあったので、下書きを何度も練り直してもらって、「提案」ではなく「筆者の意図を聞きたい」というトーンに寄せていったのですが、途中で「このIssueが失礼にならないかを気にしている」と、自分でも一度立ち止まりました。

そのタイミングで付録Aを読み直したら、`<script type="module">` + CDN import（`esm.sh`）という**buildlessな進め方が最初から明記されている**ことに気づいて、「いや、これはbuildlessな方法でしょう。あぶないあぶない、提案するのはやめます」と、早とちりでIssueを立てずに済みました。危なかった。

代わりに純粋な好奇心で「buildlessに書き換えるとどんな感じになるの？」と聞いて、`index2.html`を実際に作ってもらいました。ただ、動作確認のために別ポートを立てるとなると、SupabaseのRedirect URLsをまた追加しないといけないと分かって、「うん、やっぱめんどくさいからやめる」と、あっさり撤退しました。

サーバーを立ち上げる作業は「これは僕にやらせて」とお願いしました。環境構築の主導権は自分で握っておきたい、という気持ちがあったからです。この寄り道の後片付け中、`main.js`に`{buil`という謎の文字列が紛れ込んでいるのを見つけました。幸いまだコミットされていない変更だったので、「打ち間違いだと思うよ。元に戻して」で事なきを得ました。

## 4. 第5章 API設計 ——本物のリクエストをNetworkタブで見る

第5章はCRUDとRESTの概念回で、追加のコーディングは不要でした。「REST APIだけ復習しとこうかな」（誤変換していますが復習のことです）と頼んで、REST APIの基本（URL＝リソース、HTTPメソッド＝CRUD、ヘッダー＝認証）を復習しました。

締めにブラウザのDevTools「Network」タブを開いて自分で投稿してみたら、自分のクライアントコードの裏で本物の`POST /rest/v1/tweets`と`Authorization: Bearer ...`ヘッダーが飛んでいるのが実際に目で見えました。説明を読むだけでは得られない納得感がありました。DevToolsも使ったことのあるタブが増えてきて、身近になりつつあります。

## 5. 第6章 公開タイムライン ——下書き機能で本当にRLSを試す

`is_public`列とRLSポリシーの書き換え（`is_public or auth.uid() = user_id`）はスムーズに終わりました。ここで「その先のブラウザ側の変更は追加しなくて良い？」と聞いてみたところ、フロントを触らなくても教材の必須要件は満たすけれど、下書き機能が無いと今回のポリシーの「自分だけ見える」の部分が一度も検証されない、と言われて、それなら実際に試してみたいと思い、下書き投稿チェックボックスを実装してもらいました。

検証は自分でシークレットウィンドウを開いてやりました。「おー、下書きが見えなかった」——匿名アクセスでは`auth.uid()`が空になって、実質`is_public`だけの条件になる、という仕組みが目の前で証明された瞬間で、ちょっと感動しました。ついでに「せっかくだからサインアウトのボタンも作ろう」と、それまで無かったサインアウト機能も足しました。

## 6. 第7章 フォロー ——3アカウントでの実地検証

`follows`中間テーブル、複合主キー、自分自身フォロー禁止の`check`制約まで一通り実装しました。フロント側は「投稿者IDを表示する本格実装で行こう」と決めて、投稿者ID表示とフォロー/アンフォローボタンを追加しました。

せっかくなので、実際に3つのGoogleアカウントでログインし直して動作確認しました。結果を見て、「３つのアカウントでチェックしました。今はフォローしていない人の投稿も見えていますね。教科書通りにやってる？？」と、ちょっと不安になって聞き返しました。

でもこれはバグではなく正解でした。第7章は`follows`テーブルを作るだけで、タイムラインの絞り込みにはまだ関与していない。自分の観察から「あれ？」と気づけたのは良かったですし、絞り込みが次の第8章の仕事だとつながったのも面白かったです。

## 7. 第8章 ホームタイムライン ——N+1問題とDRY原則、AIの提案を突き返す

「みんな」タブと「ホーム」タブを切り替える形で、フォロー中の人＋自分の投稿だけに絞り込むホームタイムラインを実装しました。`follows`から`followee_id`一覧を取得し、`.in('user_id', ids)`で`tweets`を絞り込む「2段がまえ」で、教材通りの作りです。

### N+1問題を深掘り

「N+1問題をもう少し詳しく説明して」と聞いて、投稿者プロフィールを1件ずつ取得する悪い例と、`.in()`でまとめて取る良い例を教えてもらいました。実は自分がさっき書いた`loadHomeTimeline`のIDまとめ取りが、まさにこのN+1対策そのものだったと分かって、ちょっと得した気分になりました。

### DRY原則をめぐる一幕

ここが今回いちばん記憶に残っているやり取りです。「ここまでのコードはDRY原則に乗っ取っている？　opus で実行して」と、あえてOpusモデルでレビューしてもらいました。結果、「`loadTweets`と`loadHomeTimeline`の重複は整理する価値がある」という指摘があり、`fetchTweets`という共通関数への統合案が出たので、いったんその通りに直してもらいました。

でも実際にできあがったコードを見て、「うーん、コードは短くなったけど、可読性は下がったかなぁ　どう思う？」と引っかかりを覚えました。行数は減ったけれど、実際どんなクエリが飛んでいるか知るには別の関数まで見に行かないといけないし、クエリビルダーの遅延評価という前提知識も要る。ずっと大事にしてきた「一行ずつ、上から読めば分かる」というスタイルとは合わない気がして、「もどそう」と、元の素直な2関数構成に戻してもらいました。

AIのレビューや提案をそのまま受け入れるのではなく、自分の「読みにくい」という感覚を優先して差し戻せたのは、前回のハルシネーション騒動から続く「信頼するが、検証せよ」を、また違う形で実践できた気がしています。

## 8. 第9章・第10章 ——キャッシュとセキュリティの総まとめ

第9章「キャッシュ」は、公開データと個人データでキャッシュの扱いを変える（`Cache-Control: public` / `private`）という概念回でした。今のアプリ構成ではCache-Controlを直接扱う場所が無いので、実装は不要でした。

第10章「ありがちな失敗と直し方」は、これまでの章の「⚠️ハマりどころ」の総集編でした。RLS、フロントの`if`だけの隠蔽、秘密鍵の管理、XSS、キャッシュ、SQLインジェクション、連番IDの列挙、N+1——8項目のチェックリストを、自分たちのアプリのコードと照らし合わせてみたら、ほぼすべてクリアしていることが分かりました。狙って守っていたわけではなく、章を順番に追ってきた結果として自然に守れていた、というのが素直に嬉しかったです。
