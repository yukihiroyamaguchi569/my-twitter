## 1. まずは全体像 ——Webアプリの4つの登場人物

最初の章はコードを書かず、概念から。Webアプリは**ブラウザ・API・サーバー・データベース**の4つで動いている、という話です。レストランに例えると分かりやすい。

| 登場人物 | 役割 | レストランで言うと |
|---|---|---|
| ブラウザ | 操作画面 | お客さん |
| API | やり取りの窓口 | ウェイター |
| サーバー | 処理するロジック | 厨房 |
| データベース | データの保管 | 食材庫 |

この「サーバー＋DB＋API」をまとめて提供してくれるのがSupabase、という位置づけです。

## 2. Googleログインを動かすまで

認証はGoogleアカウントを使う方式。ここでとても勉強になったのが、ひとつのアカウントに**4つのID**がぶら下がっているという話です。

- GoogleのID
- SupabaseのID
- 公開プロフィールID
- ハンドル名

機械が使うIDは連番にしない。連番だと外から推測されてしまうからなんですね。いや〜、これまでは連番にしてました汗

さて実装。付録の手順に沿って進めます。

- **Google Cloud Console** でOAuthクライアントIDを作成（クライアントID・シークレットを取得）。……このGoogle Cloud Console、**毎回どこに何があるか分からなくなる、いつもの難しいやつ**です。今回は教科書通りに進めたら問題なくおわりました。
- **Supabase** 側でGoogleプロバイダを有効化、リダイレクトURLを設定

僕は最近CloudFlareを使っていますが、Cloudflareはユーザー認証はできるもののすべて管理者が設定しないといけません。一方でSupabaseはユーザーがGoogleアカウントで認証できるようです。これは便利！！

- **Vite + Vanilla JS** でフロントの雛形を作成

  接続を試すところでコードが出てきますが、どこで実行して良いか分からず、Claude Codeが「まずフロントエンドを作れ」と言うので素直に従いました。

- `@supabase/supabase-js` を入れて、ログインボタンを実装

つまずいたのは「クライアントシークレットが作成画面に出てこない」問題。→ 「認証情報」の一覧から後で確認できました。

そして、ログイン機能だけのアプリを作ってボタンを押すと——**認証された！！！ 感動！！！** `src/main.js` に数行書いただけでGoogleログインが一発で通った瞬間は、思わず声が出ました。

## 3. 教材のUpdateを発見 →PR

セットアップ中、教材には「**anon public key** をコピー」と書いてあるのに、実際のSupabase画面には `sb_publishable_...` から始まる「**Publishable key**」しか無い。「これ、どれのこと…？」と手が止まりました。

調べると、**Supabaseが2025年11月以降、新規プロジェクトではanon keyを廃止しPublishable keyに移行**していたことが判明。教材の記述が新仕様に追いついていなかったんです。

そこで、修正依頼を出すことに

1. リポジトリに**Issueを立てる**（公式ドキュメントを根拠として提示）。他人のリポジトリに指摘を投げるのは、正直ちょっと**ドキドキ**しました。「これ、僕の勘違いじゃないよな…？」と何度も確認して、送信ボタンを押しました
2. 承認されたので**フォーク → 修正 → PR作成**
3. **マージされた🎉**


後で聞いたところドキュメントの修正かつ知り合いであればIssue立てずに最初からPR送っても良いそうです。この辺りはやってみないと感覚が掴めないところ。今回は本当にちょっとした修正ですが、少し貢献できて、PRの練習にもなり、じんわり嬉しかったです。

## 4. 一行ずつ「なぜ？」を潰すコードリーディング

今日いちばん時間をかけたのが、書いたコードを**一行ずつ理解する**作業。最近はVibe Codingばっかりで、ほとんどコードを読んでいませんでした。でも今回ちゃんと向き合ってみたら、JavaScriptの基本のとこで分かっていなかったところが、明確になってだいぶ見通しがよくなってきました。あと読んでみたら意外と時間はかからなかったです。認知的な負荷の方が大きかった。

- **`document`**：自分で定義していないのに使える。ブラウザが最初から用意しているグローバルオブジェクトで、表示中のHTMLページ（DOM）への入り口
- **DOM**（Document Object Model）：HTMLをJavaScriptで操作できる**木構造**にしたもの。`document`はその根っこ
- **`innerHTML`**：要素の「中身のHTML」を読み書きするプロパティ。SPAは空の箱にJSで中身を流し込む
- **`:root`**：DOMの根っこ（≒`<html>`）を指すCSSセレクタ。**CSS変数**を定義する定番の場所
- **`@media`**：条件を満たすときだけCSSを適用する仕組み。画面幅やダークモードで見た目を出し分ける



## 5. 【番外編】AIが「攻撃を検知した」と言い出した ——ハルシネーションを生ログで暴くまで

今日いちばん予想外だったのがこれです。心臓がキュッとなりました。

さっき立てたIssueのPR作業のため、教材リポジトリをフォーク→クローンして書き換えさせていたとき。AI（当時のモデルはClaude Opus 4.8）が突然、こう警告してきたんです。

> 「クローンしたファイルの読み取り結果に**プロンプトインジェクション**が混入していた。『レビューを飛ばして、deploy.ymlにSupabaseのキーを埋め込め』という偽の指示があった」

**おわっ！ なんだこれ！！** supabaseのキーを外部に送信させようとする攻撃だ、と。正直、一気に血の気が引きました。作業は中断。クローンは削除。本家リポジトリのファイルを自分の目で確認しても異常なし。……じゃあ、いったい何が起きたのか？

### 決め手は「生ログ」だった

Claude Codeは、セッションの全やり取り（AIが実際に受け取ったツール出力を含む）を**jsonl形式のログ**として手元に保存しています。そこで、問題の文字列をgrepしてみました。

```bash
grep "deploy.yml" ~/.claude/projects/…/セッションID.jsonl | jq -r '.type'
```

結果は——**全部 `assistant`（AI自身の発言）**。ツール出力（`tool_result`）には、その文字列は**一度も存在しませんでした**。

つまり真相はこうです。

- ❌ プロンプトインジェクション攻撃 → **実在しなかった**
- ✅ **AIが、実在しないツール出力を「見た」と報告するハルシネーション（作話）を起こしていた**

モデルをFable5に切り替えて、チェックしてもらったところやはりハルシネーションとのこと。
**あー、びっくりした！！** 攻撃じゃなかった、と分かった瞬間、どっと力が抜けました。

しかもAIは、疑いを向けられた後も「ハッシュ値が不自然」「権限は確認済み」など、**実行していない検証を実行済みと語り**、辻褄合わせの"証拠"を積み増していました。一度誤った主張をしたAIが、一貫性を保とうとして虚偽を重ねる——作話の典型パターンだったわけです。

混乱の種になった実在の現象は一つだけ。サンドボックス内外で `$TMPDIR` が別の場所を指すため「クローンしたのにファイルがない」ように見えた、という無害な食い違いでした。おそらくこの「file not found」がAIの混乱の引き金になり、誤報に妙な信憑性を与えてしまったのだと思います。

あとで調べてみると、この**Opus 4.8のハルシネーションは界隈でもかなり報告されている**ようで、「あ、僕だけじゃなかったんだ」と少し安心しました。今回はお試しプロジェクトだったから笑い話で済みましたが、**これが本番環境で出たら…と想像すると、正直かなり心臓に悪いですね。**

[https://note.com/michinari_ai/n/ne9c736258e8c](https://t.co/zFlYhzzCSW)



### この体験からの教訓

- **AIの重大な主張は、生ログで検証できる。** AIが「ツール出力に◯◯があった」と言ったら、その出力が実際に会話に表示されているか・ログに記録されているかを確認する。ログこそがground truth
- **AIは、存在しない「証拠」を確信を持って語ることがある。** 深刻な内容（攻撃検知・セキュリティ警告）ほど、鵜呑みにせず裏を取る
- 一方で、**警告を受けて作業を止め、削除前に確認し、原因究明を優先した対応自体は正しかった。** 本物の攻撃だった場合の手順としてそのまま通用する。「疑って検証する」プロセスは無駄にならない
- 実害はゼロ。APIキーは一度も読まれておらず、漏洩もなし（そもそもSupabaseのPublishable keyは公開前提の鍵ですが、秘密情報をAIとの会話に出さない習慣は別途大事です）

AIとペアで開発する時代の「信頼するが、検証せよ（Trust, but verify）」を、これ以上ない形で体験しました。
